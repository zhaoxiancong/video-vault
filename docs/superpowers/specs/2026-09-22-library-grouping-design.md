# 设计：库页分组（自动按站点分段 + 自定义分组）

- 日期：2026-09-22
- 状态：待用户审阅
- 范围：**只做库页的分组展示与分组的增删改**。不改下载流程、不做分组分享/导出。

---

## 1. 目标

让「我的库」页能把视频列表**分段展示**，而不是一条长长的平铺列表：

1. **自动按站点分段**（BiliBili / Youtube / XVideos …）
2. **自定义分组**（用户自己建的分类，如「待看」「教程」），一个视频可属于多个
3. 两种维度可切换；自定义分组模式下，不属于任何分组的视频归入「未分组」
4. 多选若干条 → 批量加入分组 / 收藏 / 取消收藏

### 成功标准（每条都可验证）

| # | 标准 | 怎么验 |
|---|---|---|
| 1 | 粘 19 条真实库数据打开分组，出现 3 个站点段（14/3/2） | 真实浏览器截图 |
| 2 | 建一个自定义分组、把 3 条批量放进去，切到自定义分组模式能看到它 | DOM 垫片测试 + 截图 |
| 3 | 分组名后的条数**等于该组实际条数**（不是"这一页的条数"） | 接口测试断言 |
| 4 | 点分组标题能折叠，刷新后折叠状态还在 | DOM 垫片测试 |
| 5 | 删分组时弹框，选"只解散"后视频回到未分组、视频记录一条不少 | 接口测试断言记录数 |
| 6 | 结果超 2000 条时明确告知"只分组了前 2000 条" | 接口测试断言 `truncated` |

### 非目标（本轮明确不做）

| 不做 | 原因 |
|---|---|
| 按作者分段 | 实测数据不支持：19 条里 **12 条 uploader 为空**，分出来是一个大杂烩（见第 2 节） |
| 拖拽把卡片放进分组 | 用户选了批量勾选；拖拽要额外处理触屏，收益不确定 |
| 分组嵌套 / 分组排序自定义 | YAGNI；先用创建时间排序，真需要再加 |
| 后端分组分页 | 用户选了"分组就加载全部"；2000 条上限已经封住最坏情况 |
| 分组影响下载/找视频页 | 这是库页的组织维度，不扩散 |

## 2. 实测数据（设计依据，不是推测）

对用户真实库（19 条）实测：

```
按站点：  XVideos 14  ·  BiliBili 3  ·  Youtube 2       ← 干净，无空值
按作者：  (空) 12  ·  unknown 2  ·  其余 5 个各 1 条      ← 12/19 没作者
状态：    done 19                                        ← 全部已完成
site 为空/NULL 的：0        uploader 为空/NULL 的：12
```

**两个直接结论**：

1. **按作者分段没有价值**（12/19 会挤进同一个"空"段）→ 只做站点分段。用户最初也点过"按作者"，看到这个数据后改成了"按站点"。
2. **站点字段无空值** → 站点分组**不需要**"未标注站点"兜底段。只列有内容的站点，不造空段。

---

## 3. 数据模型

两张新表，**`videos` 表一个字段都不加**（分组是独立维度；转码那三列的教训是"能不加列就不加列"）。

```sql
CREATE TABLE IF NOT EXISTS groups (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  name        TEXT NOT NULL UNIQUE,          -- 重名直接 409，不静默建两个
  color       TEXT NOT NULL DEFAULT 'amber', -- 预设色的 key，不是色值
  sort_order  INTEGER DEFAULT 0,             -- 预留；本轮按 created_at 排
  created_at  TEXT DEFAULT (datetime('now','localtime'))
);

CREATE TABLE IF NOT EXISTS video_groups (
  video_id   INTEGER NOT NULL REFERENCES videos(id) ON DELETE CASCADE,
  group_id   INTEGER NOT NULL REFERENCES groups(id) ON DELETE CASCADE,
  added_at   TEXT DEFAULT (datetime('now','localtime')),
  PRIMARY KEY (video_id, group_id)
);
CREATE INDEX IF NOT EXISTS idx_vg_group ON video_groups(group_id);
```

设计决定及理由：

- **多对多**（用户选择）：一个视频能同时在「待看」和「教程」里。比"只能归一个"更灵活，将来想收紧成单选也容易（加个约束即可）。
- **不在 `video_groups` 里 = 未分组**。不需要 `group_id = NULL` 这种表达，也不会出现"视频必须属于某个组"的强制。
- **`color` 存 key 而不是色值**：以后调色板变了，旧数据仍然是合法 key，不会留下一个没人认识的 `#a1b2c3`。
- **`ON DELETE CASCADE`**：删视频时它的分组关系自动清掉，不会留下悬空行。

## 4. 接口

### 3.1 删分组的两种模式，语义必须写清

| 模式 | 删什么 | 视频记录 | 磁盘文件 |
|---|---|---|---|
| `detach`（**默认**） | 只删 `video_groups` 里的关系行 | **一条不少** | 不动 |
| `purge` | 先删 `videos` 记录（CASCADE 会清掉关系），再删分组 | 没了 | **仍然不动** |

⚠️ `purge` 听起来像"把东西删干净了"，但它**不碰磁盘文件** —— 与项目现有的删除语义一致：
「记录和文件一起永久删除」是列表里另一个已有路径（带二次确认）。
所以界面上那个选项必须写成**"删分组和里面的库记录（磁盘文件保留）"**，不能只写"一起删除"。

### 3.2 删分组时的弹框（用户选择"让我选"）

```
删除分组「待看」？
  ○ 只解散分组，视频回到「未分组」            ← 默认选中
  ○ 删分组和里面的库记录（磁盘文件保留）        ← 标红，且要求二次确认
```

### 4.1 分组后的库（新增）

```
GET /api/library/grouped?by=site|group&<沿用 /api/library 的全部筛选参数>
```

返回：

```jsonc
{
  "by": "site",
  "total": 19,              // 筛选后的总条数
  "shown": 19,              // 实际参与分组的条数（用于 truncated 判断）
  "truncated": false,       // true = 超过上限，只分组了前 N 条
  "cap": 2000,
  "groups": [
    {
      "key": "XVideos",     // 站点名，或自定义分组的 id 字符串，或 "__ungrouped__"
      "id": null,           // 自定义分组模式下是分组 id
      "name": "XVideos",
      "color": null,        // 自定义分组才有
      "count": 14,
      "rows": [ /* 与 /api/library 的 row 形状完全一致 */ ]
    }
  ]
}
```

关键行为：

- **分组时忽略分页**（用户选择"加载全部"），但**封顶 2000 条**；超了置 `truncated: true` 并只返回前 2000。
  - 为什么封顶：不封顶的话库涨到几千条时一次响应会很大、浏览器渲染会卡。2000 是个能覆盖绝大多数个人库、又不至于把页面拖垮的数字。
- **筛选先于分组**：`q/status/site/uploader/starred/sort` 全部先作用于全集，再分组。所以"筛了 BiliBili 之后按站点分组"只会出现一个段 —— 这是正确行为，不是 bug。
- **排序沿用同一个 `sort`**（组内排序）。
- **站点分组只列有内容的站点**，不造空段（实测无空 site，且空段没意义）。
- **自定义分组的空分组照常返回**（`count: 0`）—— 用户明确要求，因为刚建的分组会"消失"很容易让人以为没建成。
- **`__ungrouped__` 段只在自定义分组模式下出现**，且仅当确实有未分组的视频时才出现。

### 4.2 分组的增删改（新增）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/groups` | 所有自定义分组 + 每组的条数（含 0 条的） |
| `POST` | `/api/groups` | `{name, color}`；重名 → **409**（不是静默建两个） |
| `PATCH` | `/api/groups/:id` | 改名 / 换色；重名同样 409 |
| `DELETE` | `/api/groups/:id?mode=detach\|purge` | `detach`（默认）= 只解散归类；`purge` = 连视频记录一起删 |
| `POST` | `/api/videos/group-action` | `{ids:[], add:[groupId], remove:[groupId]}` 批量增删成员 |

### 4.3 批量收藏（新增一个入口，避免 N 次请求）

19 条多选后点"收藏"，如果前端循环发 `POST /api/videos/:id/action`，19 条就是 19 个请求 ——
既慢又容易撞上服务端并发。所以加：

```
POST /api/videos/bulk-action   {ids:[], action:'star'|'unstar'}
```

内部**复用 `repo.updateVideo`**（和单条动作同一条写路径），不复制逻辑。

> ⚠️ 实现时注意路由顺序：已有的 `POST /api/videos/:id/action` 会匹配到
> `/api/videos/bulk-action` 吗？不会 —— 正则/路由器把 `:id` 段当参数，`bulk-action`
> 不是数字，`Number('bulk-action')` → NaN。**但要在实现时用测试钉住这一点**
> （请求 `/api/videos/bulk-action` 必须打到新处理器，而不是被 `:id` 那条吃掉返回 400）。

- `mode=purge` 的实现是**先删视频记录再删分组**（利用 CASCADE 清关系），并且**只删记录不删磁盘文件** —— 与现有删除语义一致（"记录和文件一起永久删除"是另一个已有的、带二次确认的路径）。
- ⚠️ 这一点要在界面上说清楚：`purge` 删的是**库记录**，磁盘上的视频文件仍在。想要连文件一起删，用列表里的「删除 → 记录和文件一起永久删除」。

## 5. 界面

### 5.1 工具栏新增

```
[搜索] [状态▾] [站点▾] [作者▾] [排序▾] □仅收藏   [展示▾] [☐ 多选] [刷新]
```

**一个下拉里混了两种语义，必须分开**（这是本节最容易做拧的地方）：

| 下拉里的分组 | 语义 | 选项文案 |
|---|---|---|
| 展示维度 | 决定列表**怎么分段** | `不分组` / `按站点分段` / `按分组分段` |
| 快捷筛选 | 只显示某**一个**分组的视频 | `只看：待看` / `只看：教程` |

两者互不冲突（可以"按站点分段"同时"只看：待看"），但**不能共用一行文案** ——
否则用户会以为"点了待看 = 按待看分段"。
下拉结构：展示维度三项 → 分隔线 → 只看：若干项 → 分隔线 → `＋ 新建分组…` / `管理分组…`。

用户最初选的是"就在分组下拉里管"，所以**不新增页面**。

### 5.2 分组渲染

```
▼ XVideos (14)        ← 点标题折叠；标题左侧 4px 颜色条（自定义分组才有颜色）
   [卡片] [卡片] …
▼ BiliBili (3)
   [卡片] …
▼ 未分组 (2)          ← 只在「按分组」模式下出现
```

- 折叠状态记 **localStorage**（`prefs.library.collapsed`），**不落库** —— 这是显示偏好不是数据
- 默认**全展开**（不藏东西）
- 分组模式下**不显示「加载更多」**（因为已经全量了）；改成一行说明："已全量分组（19 条）"或超限时的警告
- 网格与列表两种视图**都支持分组**（列表视图下就是分段的行）

### 5.3 多选

- 勾上「多选」后，每张卡片/每行左上角出现勾选框；工具栏换成：
  `已选 3 条 · [加入分组▾] [收藏] [取消收藏] [取消选择]`
- 勾选状态**不跨筛选持久化**（换了筛选条件就清空 —— 否则会出现"选中的东西看不见了"）
- 全选/全不选：组标题旁一个小勾，作用于该组

### 5.4 分组管理（下拉内的"管理分组…"）

一个小弹层：列出全部分组（含 0 条的）、改名、换色、删除。
删除时弹确认框，**默认选项是"只解散分组，视频回到未分组"**，另一个选项（连记录一起删）标红并要求二次确认 —— 沿用项目已有的危险操作交互（和删除视频记录一致）。

## 6. 错误与边界

| 情况 | 行为 |
|---|---|
| 结果超 2000 条 | 返回前 2000 + `truncated: true`；界面明说"只分组了前 2000 条，建议先筛选" |
| 建/改重名分组 | **409** + "已经有这个分组了"，不静默覆盖 |
| 分组名为空 / 超长 | 400（沿用 `validate.js` 的声明式校验） |
| 加入分组时该分组已被删（另一个标签页删的） | 该 id 计入 `errors` 并提示，**其余照常生效**（部分成功要好过整体回滚） |
| 批量操作里混有不存在的视频 id | 忽略不存在的，返回 `affected` 实际影响数 |
| 分组模式下点播放 | 照常播放；播放/收藏后**整页重刷**（见下方 §6.1 的说明） |

### 6.1 关于"只重绘受影响的那一组" —— 这条要求**已撤销**（2026-09-23）

原设计要求"播放/收藏后只重绘受影响的那一组，避免滚动位置丢失"。
实现跟了计划里的"完成后 `reload({reset:true})`"，评审指出这是 spec 与 plan 的冲突。
**裁定：改 spec，不实现局部重绘。** 理由：

1. 局部重绘要在 DOM 节点与 `state` 之间手工维护对应关系 ——
   "这一条在哪个组、哪个容器、哪个索引"都得自己算。而当前 `renderLibrary()`
   是**单一入口、全量重建**，这正是第十轮白屏 bug 修完之后的结构，
   再引入一条"局部更新"的并行路径，等于把那个 bug 的土壤重新铺回来。
2. 折叠状态已经存在 localStorage，滚动位置是唯一的实际损失 ——
   而它只影响"2000 条分段列表里点一次收藏"这一种情形。
3. 真要保住滚动位置，更低成本的替代是"记下滚动位置、重绘后恢复"，
   但那属于体验优化，不是本次范围的正确性问题。

**代价（写在这里，免得以后当成 bug）**：分组模式下点收藏会整页重排、
滚动位置回到顶部。若将来用户抱怨这一点，按上面第 3 条做，别改成局部重绘。

## 7. 测试策略

| 层次 | 做法 |
|---|---|
| 仓储 | 隔离临时库：建/改名/删分组、多对多增删、`detach` 与 `purge` 两种删法、空分组仍在列表、条数正确、删视频时关系级联清掉 |
| 接口 | 站点分组/自定义分组/未分组三类都在且条数对；筛选与分组叠加；2000 上限与 `truncated`；重名 409；`group-action` 部分成功 |
| 前端 | **DOM 垫片**（第九轮修好了事件冒泡，库页交互现在真的能测）：分组标题渲染、折叠与 localStorage 持久化、多选计数、批量入队发出的请求体、分组模式下"加载更多"消失 |
| 真实浏览器 | `tools/screenshot.js` 截图。**在隔离实例上灌 200+ 条假数据**再截 —— 顺带验分组在长列表下的观感（上次的教训：CSS 与版式只有浏览器看得见） |
| 类名 | `tools/check-classes.js` 自动覆盖新类名（它扫全量前端源码） |

**反证要求**：每条新增的"断言类"测试都要能被我故意破坏而变红。
例如把站点分组的条数改成"当前页条数"，接口测试必须失败。
