# 视频下载工具 · Video Vault

一个跑在你自己电脑上的**视频下载 + 个人视频库**工具。粘链接进去，它负责下载、归类、入库；
下载完的片子能搜索、能筛选、能直接在网页里播放，还能一键转成剪辑软件好用的格式。

---

## 1. 怎么用（三步）

1. 双击 **`启动.cmd`**
2. 浏览器会自动打开 `http://127.0.0.1:8787`
3. 在「添加下载」页把视频链接粘进去 → 点「加入下载队列」

关掉那个黑色命令行窗口 = 停止工具。**没下完的任务不会丢**，下次打开点「全部继续」接着下。

> 不想用 bat，也可以命令行启动：
> ```powershell
> cd D:\AI\works\20260920_视频下载工具
> .\启动.ps1              # 默认 8787 端口
> .\启动.ps1 -Port 8899 -NoBrowser
> ```

## 2. 你的三个真实需求，分别落在哪
被 grill 出来的原话是：**建自己的学习资料库**、**存下来防丢**、**当剪辑素材用**。
这三个需求其实**互相冲突**——防丢要"原始文件别动它"，剪素材要"统一格式方便剪"。
工具是按这个冲突设计的：

| 需求 | 实现方式 | 在哪看 |
|---|---|---|
| **防丢** | 原始文件**只写一次、永不改动**；重名不覆盖；带 URL 去重，同一个片子不会重复下 | 下载目录里的原始文件 |
| **建库** | 每条下载写进 SQLite：标题/作者/站点/时长/分辨率/编码/简介/封面，支持关键词搜索 + 站点/作者/状态筛选 + 收藏 + 备注 | 「我的库」页 |
| **剪素材** | 转码产物**另存**在 `downloads\_converted\`，可选「H.264 1080p / 720p」「H.265」「仅换容器 mp4」「抽 MP3」 | 库 → 更多 → 转码 |

也就是说：**归档层（原始文件）/ 工作层（转码产物）/ 检索层（数据库）三者分开**，
互不干扰。你剪坏了转码文件，原始文件还在；你删了库记录，也能选择保留文件。

## 3. 功能一览（一期已实现）

### 下载
- **批量粘链接**：一行一个，可一次丢几十条；自动去重
- **通用站点**：交给 yt-dlp 的 1800+ extractor，不挑站
- **播放列表 / 合集 / 频道自动展开**：喂一个列表地址，自动拆成一堆单集排队
- **清晰度**：最高可用 / 4K / 2K / 1080p / 720p / 480p / 360p / 最小体积
- **仅音频**：抽成 MP3
- **并发 2**（可调）：模拟一个人正常看片的节奏，降低被风控的概率。限速默认关闭，想降风险再开
- **实时进度**：进度条 + 速度 + 剩余时间 + 当前阶段（下载中 / 合并中 / 转码中）
- **可展开的原始日志**：出问题时能直接看到 yt-dlp 说了什么
- **暂停 / 继续 / 取消 / 重试 / 删除**，中断后**手动点继续才续传**（不偷偷跑你的流量）

### 页面状态会记住，刷新不丢

服务端的队列和数据库本来就是持久的，所以**刷新浏览器不会丢任务**：

- **最近任务**面板：列出已完成/失败/暂停/取消的任务（默认收起，点「展开」）。
  每条都能**播放、重新下载、看日志、删除**。
- 你填的东西也持久化在本机（localStorage）：粘贴框内容、下载内容、清晰度、限速、
  上次的提交报告、最近任务的展开状态、库页的布局与筛选条件。
- 刷新页面后，队列里正在跑的任务会重新出现并继续显示进度（服务端在跑，不是前端在跑）。

### 删除的两种模式（都不会误删）

每条任务右侧有「删除」，点它会问你：

| 选项 | 结果 |
|---|---|
| **1｜只从列表删掉（默认）** | 记录消失，**磁盘上的视频文件保留** |
| 2｜记录和文件一起永久删除 | 会再确认一次，确认后才删文件 |

> 默认值是"保留文件"，所以**直接回车不会毁数据** —— 下载好的视频往往来之不易，
> 一个误点就永久删掉是不可接受的。
> 「最近任务」面板上的「清空已完成记录」同理：**只清列表，不动文件**。

### 库
- 缩略图网格 / 列表两种视图
- 关键词搜索（标题、作者、简介、链接）
- 按 状态 / 站点 / 作者 筛选，按 加入时间 / 标题 / 体积 / 时长 排序，仅看收藏
- **网页内直接播放**（支持拖动进度条 —— 服务端实现了 HTTP Range）
- 收藏、备注、复制文件路径、删除记录（可选是否连文件一起删）

### 转码（剪辑用）
| 预设 | 说明 |
|---|---|
| 仅换容器（mp4） | 秒完成，不重编码；mkv 转 mp4 用这个 |
| H.264 1080p | **剪辑软件最通用**，推荐 |
| H.264 720p | 体积小 |
| H.265 1080p | 更小，老设备可能不认 |
| 抽音频 MP3 | 当播客听 |

## 6. 开发时踩过的坑（改代码前必读）

这几条都是**实测撞出来的**，不是推测。改相关代码前先看一眼，能省你几个小时。

### 坑 1：不能捕获子进程的输出（沙箱限制）
当前运行环境**禁止 `spawn` + pipe 读子进程 stdout**（会抛 `EPERM`）。
所以本项目所有子进程一律用**文件描述符重定向**：
- 下载进度：yt-dlp 直接写进 `data\logs\video-<id>.log`，服务端**轮询 tail** 这个文件
- 短命令（`--version`、取元数据）：fd 指向临时文件，跑完读文件

副作用是好的：每个任务都有完整原始日志，排错很方便。

### 坑 2：yt-dlp 单文件版跑不起来
官方 `yt-dlp.exe`（PyInstaller onefile）会在系统 `%TEMP%` 里自解包，沙箱拒绝，
报 `Failed to create parent directory structure`。
**必须用目录式分发包 `yt-dlp_win.zip`**（exe + `_internal` 同级）。
程序里用的是 `tools\bin\ytdlp-win\yt-dlp.exe`。

### 坑 3：中文路径会变乱码（最阴的一个）
子进程通过 fd 重定向写文件时，中文 Windows 默认按**系统 ANSI 代码页（GBK）**编码，
于是日志里的路径变成 `...\20260920_??Ƶ????\...`，`fs.existsSync()` 永远失败，
**文件永远收不了尾**。
两个修法一起用：
- 给子进程设 `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8`
- 最终文件路径用 `--print-to-file`（yt-dlp 自己以 UTF-8 落盘），**不走 stdout**

### 坑 4：进度模板绝不能交给 yt-dlp 生成结构化格式
这里连撞两次：
1. 用 `%(...)s` 把 `_percent_str` 插进 JSON → 得到 `{"p":  0.5%}`，**不是合法 JSON**
2. 改用 `%(...)j`（JSON 编码）→ 字符串字段好了，但**数值字段取到 `NA` 时仍输出裸 `NA`**
   （`{"frag":NA}`），照样非法

**最终方案：管道分隔纯文本**，服务端自己解析：
```
VVP|  0.5%|1024|223779|68430.4|3|NA|NA      ← 下载进度
VVP|Merger|started                          ← 后期处理
```
`NA` 只是自己那一格的值，永远破坏不了整体结构。相关代码见
`app\lib\config.js` 的 `PROGRESS_TEMPLATE` 和 `app\lib\ytdlp.js` 的 `parsePipeLine`。

### 坑 5：高清流要合并进 mkv
YouTube 高清普遍是 vp9/av1 + opus，**mp4 容器装不下**，强行 mp4 会让合并直接失败。
所以视频统一合并进 `.mkv`（任何播放器都能放）。想转 mp4 就用转码预设「仅换容器」。

### 坑 6：验证语法不要用 `require()`
`node -e "require('./server.js')"` 会**真的把服务启动起来**然后卡住。
用 `node --check <file>`。

### 坑 7：`[hidden]` 会被任何 `display` 规则顶掉（这个坑真把界面弄瘫过）
浏览器给 `[hidden]` 的默认样式是 `display:none`，但它**优先级低于任何 class 选择器**。
所以只要组件里写了 `display:flex`，`hidden` 属性就完全失效。

当时的后果：`.modal { display:flex }` 让播放弹层的**全屏深色遮罩从页面加载起就一直
盖在最上层**，用户打开页面后点什么都没反应，看起来像"关闭按钮坏了"，其实是整个
界面被一层看不见的膜罩住了。

修法是样式表开头的这一行，**它是整个界面能用的前提**：
```css
[hidden] { display: none !important; }
```
同类隐患还有 `#libList`（`.list { display:flex }`）。以后新增任何"默认隐藏"的组件，
都不要依赖 `hidden` 属性裸奔，要么加这一行兜住，要么显式写 `.xxx[hidden]{display:none}`。

### 坑 8：沙箱里起不了 Chrome，UI 测试要提权
Chrome 的 crashpad 要 `OpenProcess`、多进程 IPC 要命名管道，在受限沙箱里全被拒
（`Check failed: ... 拒绝访问。(0x5)`），`--single-process` / `--no-sandbox` 都救不了。
所以 `app\uitest.js`（真实浏览器 UI 冒烟测试）**需要在放宽权限的环境下运行**。
它用 CDP 协议 + `elementFromPoint` 逐元素校验"这个坐标上到底是哪个元素"，
专门用来抓"被遮挡 / 点不动"这类靠读代码抓不到的 bug。

### 坑 9：进度条整场卡在 99%（真实发生过的 bug）
**错误假设**："看到后处理器 = 下载已经结束"。
于是代码一见到任何 postprocessor 就把进度顶到 99、状态改成"处理中"。

**为什么错**：yt-dlp 的 `ThumbnailsConvertor` 会在**下载开始之前**就先执行一次。
结果进度条从开场就被钉死在 99%，而真实下载从 0.1% 一路走到 99.4%，
整个过程（那次是 689MB / 4 分钟）用户看不到任何进度。

**正确做法**：区分"下载阶段"和"后期处理阶段"。
只有 `Merger` / `ExtractAudio` / `VideoConvertor` / `VideoRemuxer` / `Fixup`
出现在**已经收到过下载进度之后**，才算进入后处理（见 `POST_STAGE_RE`）。

**附带发现**：yt-dlp 的多条流（视频流、音频流）会**各自从 0% 走到 100%**，
所以进度条一定会"归零一次"。这不是 bug，但必须告诉用户，
否则看起来就像坏了 —— 界面现在会显示「下载中（第 2 条流）」。

### 坑 10：错误信息里存进去的是一段进度帧
`cleanError()` 原先取"日志最后一行"，而进度帧恰好排在最后，
于是数据库里的 `error` 字段变成 `VVP|100.0%|21039208|...` 这种鬼东西，
用户完全看不出发生了什么。

修法：先把 `VVP|` / `VVAULT_` / 进度条 / `Deleting ... file` 这些噪音行全部排除，
再找 `ERROR:` 行；如果只是笼统的 `Postprocessing:`，取它**后面**那行（真正的原因在那）。

### 坑 11："文件存在" ≠ "文件完整"
下载被中断会留下半截分片，yt-dlp 合并时读到坏数据直接报
`Invalid data found when processing input`，但最终文件确实躺在磁盘上 ——
只判断 `fs.existsSync()` 会把它当成下载成功。

现在的做法：用 **ffprobe 实测**产物（有时长、视频文件还要有分辨率），
不合格就清掉残留 + **自动重下一次**（只重一次，避免坏源无限循环）；
合并成功后主动清理 `.fXXX` 中间分片，防止残留污染下一次下载。

### 坑 12：抖音网页版复制出来的地址 yt-dlp 不认
在抖音网页版点开视频，地址栏是
`https://www.douyin.com/jingxuan?modal_id=7671972624104197391`
或 `https://www.douyin.com/user/xxx?modal_id=...`，
而 yt-dlp 只认 `/video/<id>`，直接粘会报 `Unsupported URL`。

**这类"粘进去就说解析失败"最让人摸不着头脑**，所以在入口做了归一化
（`ytdlp.normalizeUrl()`），把 `?modal_id=<数字>` 自动转成 `/video/<数字>`，
界面上也会显示"已自动识别为视频地址"。

> 归一化后抖音仍会报 `Fresh cookies (not necessarily logged in) are needed` ——
> 抖音现在强制要求 Cookie，这属于二期「登录态」的范围。

### 坑 13：异步调度器写成了同步无限递归（最严重的一个）
**症状**：服务端跑不到 2 分钟就 `FATAL ERROR: Reached heap limit ... JavaScript heap
out of memory`，堆涨到 4GB 崩溃；同时所有接口超时、界面完全没反应。

**根因**：为了给下载加"封面能不能嵌"的判断，我把 `_start()` 改成了 `async`
（里面 `await canEmbedThumbnail()`）。但把任务状态从 `queued` 改成 `downloading`
的代码**在 await 之后**。于是 await 让出控制权的那一刻任务**还是 `queued`**，
此时任何 `kick()` 都会让 `_schedule()` 把它再捞起来启动一次 ——
新的一次又同步跑到 await，又 kick，又启动……**同一毫秒内 `_start` 被调用上千次**，
实测堆内存每秒涨约 50MB。

**三道防线（少一道都不行）**：
1. `kick()` 改成 `setImmediate` 异步调度，打断同步递归链
2. `_schedule()` 在调用 `_start()` **之前**就把 id 放进 `running` 占位
3. `_start()` 在**任何 await 之前**完成状态迁移

**定位过程**（这类 bug 靠读代码很难发现，方法是可复用的）：
- 先采样进程内存 → 发现是"每秒 +50MB"而不是"慢慢泄漏"→ 说明是死循环不是泄漏
- 给 `_start()` 加步骤 trace → 日志里同一毫秒内成百上千行相同记录 → 实锤递归
- ⚠️ trace 本身也吃内存（海量字符串堆在 stdout 缓冲里），定位完必须删掉

**教训**：把同步函数改成 `async` 时，必须检查所有"读状态决定要不要处理"的地方 ——
状态迁移一定要发生在第一个 `await` 之前。

### 坑 16：insertVideo 的白名单静默丢字段
`db.js` 里"插入"和"更新"原本各维护一份字段白名单，两边会各自漂移。
实际后果：`insertVideo()` 的白名单漏了 `file_path` / `file_size` / `thumbnail_path`，
**传进去的字段被静默丢弃** —— 记录插进来了，但文件路径是 `null`，不报错、不崩溃。

这类"静默丢数据"最难查。修法是两份名单合成一份 `WRITABLE_COLS`，
并加了开发期自检：`VAULT_STRICT_DB=1` 时，传了不在白名单里的键就直接抛错。

> 这个 bug 是写"同文件去重"功能时被测试逼出来的 —— 合并逻辑依赖 `file_path`，
> 而测试构造的记录 `file_path` 是 null，才发现字段根本没存进去。

### 坑 17：拿用户的真实数据做破坏性操作测试
验证「清空已完成记录」时，我**直接对用户的真实库执行了 `clearFinished`**，
结果真删掉了 7 条记录。文件还在磁盘上（所以能靠 `rebuild-library.js` 重建），
但库空了、封面映射丢了 —— 这是我造成的实际损失，不是"测试环境"问题。

**破坏性操作（删除/清空/覆盖）的正确测法**：

1. 先插入**自己的**测试记录（用带时间戳的唯一 URL，避免撞唯一约束）
2. 只对这些记录执行操作
3. 立刻清理，并断言"操作前后的记录数一致"，确认没污染用户数据

这条已经写进 `selftest.js` 的回归测试（"破坏性测试没有污染用户库"）。

**附带的救命工具**：`rebuild-library.js` —— 库万一没了，它能扫磁盘上的视频文件
（命名规则 `站点\作者\标题 [清晰度].ext` 本身带信息）+ ffprobe + 封面时间戳，
把记录重建回来。实测能把 6 个视频连同分辨率/时长/封面全部恢复。

### 坑 18：`clearFinished` 之类的批量删除必须只删记录
一开始我担心"清空已完成"会不会连文件一起删。实现和测试都确认了：
**它只删数据库记录，磁盘文件一律保留**（要删文件必须逐条用「删除」并明确选择）。

### 调试工具（`app/` 下，都带硬超时，不会无限挂起）

| 工具 | 用途 |
|---|---|
| `selftest.js` | 111 项自检，含 20+ 个历史 bug 的回归测试（含破坏性操作的安全断言） |
| `e2e.js` | 24 项 HTTP 端到端集成测试 |
| `uitest.js` | 24 项真实浏览器 UI 测试（需放宽权限，见坑 8） |
| `lint-undefined.js` | 静态检查"调用了未定义的函数（含漏导入）"—— 见坑 14 |
| `rebuild-library.js` | **从磁盘重建视频库**（库万一丢了用这个，见坑 17） |
| `diagnose.js` | 下载诊断：逐秒打印进度/速度/原始日志，定位"慢"和"卡" |

### 坑 14：删调试代码漏删一处，整个功能静默失效
为了定位内存问题，我加过一些调试输出（`trace()`、`_probe()`）。事后删的时候**漏了一处**，
于是 `_start()` 一进 try 就抛 `ReferenceError: trace is not defined`，
被 catch 吞掉后变成 **"解析失败: trace is not defined"** ——
表面看是"解析失败"，实际是**所有新任务全部下载失败**，报错信息完全指不到真正原因。

同类问题还有一个：`startTranscode()` 里用了 `spawn()`，但文件顶部只导入了 `spawnSync`，
所以**转码功能从来就没能用过**，一调用就 `spawn is not defined`。

`node --check` 只查语法，这两种都抓不到；接口测试也没覆盖到那些分支。
所以做了 `lint-undefined.js`：扫出所有"像函数调用"的名字，逐个确认有没有被声明过
（函数声明/类/const/参数/解构/import）。

> 这个 linter 自己也是调试了好几轮才可靠，两个教训值得记：
> 1. **不要用正则剥注释和字符串** —— 在 CRLF + 引号嵌套下一次吞掉了两万字符的代码。
>    改成"按行跳过注释 + 只认行首调用"，不做代码剥离。
> 2. 判"方法声明"还是"函数调用"要看**行尾**：`foo(...) {` 是声明，`foo(...);` 是调用。
>    只看行首会把两者混淆（我的第一版就是这样，导致 linter 完全抓不到 `trace`）。

**教训**：加临时调试代码时就要想好怎么删干净；能不加就不加，必须加就集中在一处并留 TODO。

### 坑 15：粘"页面链接"时只报一句 `Unsupported URL`
用户粘的往往是**页面地址**而不是某个视频的地址，例如
`https://www.xvideos.com/best/2026-08`（分类列表页）、站点首页、
或带一堆参数的频道页。yt-dlp 对这种地址只会回一句
`Unsupported URL: ...`，**用户完全不知道下一步该做什么**，还容易以为工具坏了。

现在的做法（`lib/urldiag.js`）：解析失败时额外抓一下那个页面，
统计里面有多少个"像视频详情页"的链接，据此给出结论：

| 诊断到的类型 | 给用户的提示 |
|---|---|
| `listing`（含 ≥5 个视频链接） | 这是一个页面链接，不是单个视频……（检测到约 27 个视频链接）请点进具体那个视频 |
| `single-page-no-extractor` | 页面有视频但 yt-dlp 没解析器，可试播放器直链 |
| `not-a-video-page` | 不像视频页（附页面标题），请确认复制的是视频地址 |
| `http-error` | HTTP 404/403，可能失效或需登录 |
| `fetch-failed` | 地址读不到，确认可访问 |

**边界（刻意设的）**：只在解析失败时才抓、10 秒超时、最多读 512KB、
失败就静默退回原始报错。**不做整站爬虫** —— 那既超出范围也越过站点条款。

> 提示文案里**不要写 Markdown 记号**（`**粗体**` 之类）：
> 前端用 `textContent` 显示，星号会原样露出来。这条也写进了回归测试。

## 7. 设置项

「设置」页可改，改完即时生效（存在数据库里）：

| 项 | 默认 | 说明 |
|---|---|---|
| 下载目录 | `downloads\` | 想放 D 盘别处就改这里 |
| 并发任务数 | 2 | 同时下几个。调高会更容易被站点风控 |
| 每任务限速 | **不限速** | 「添加下载」页也能直接改。想降风控风险再开 |
| 分片并发数 | 8 | 单个任务内部并行分片数，对 HLS/DASH 流提速明显 |
| 失败重试次数 | 2 | |
| 按站点/作者建子目录 | 开 | |
| **读取浏览器登录态** | **不用** | 见 8b 节。必须显式开启，不会偷读 |
| **cookies.txt 文件** | 空 | 优先级高于浏览器；Netscape 格式 |

### 关于下载速度

- **限速是最大的变量。** 早期版本默认 5 MB/s，下大文件时它成了唯一瓶颈
  （实测被完整吃满：峰值 4.90 MB/s、平均 2.82 MB/s）。现在默认不限速。
  如果你的库是早期版本建的，程序启动时会自动把这项迁移成"不限速"
  （控制台会打印 `[迁移] 限速 5 MB/s → 不限速`），也可以在界面上自己改。
- **各站速度差异极大。** YouTube 通常能跑满带宽；B 站经常把单连接限到
  0.1~0.5 MB/s（那是站点侧的限速，不是本工具造成的，换代理也未必好）。
- 想再快可以调高「并发任务数」和「分片并发数」，代价是被风控的概率上升。

### 关于进度条

一次下载要下**两条流**（视频流 + 音频流），yt-dlp 是**先后**下的，
所以进度条会：`0→100%`（视频流）→ **归零** → `0→100%`（音频流）→ 合并。

**归零不是 bug**，界面会显示「下载中（第 2 条流）」告诉你在下第二条。
下载完成后的合并/嵌入封面阶段会显示「处理中 · Merger」。

## 8b. 登录态（Cookie）怎么用

有些站点不登录就下不动：

| 站点 | 症状 |
|---|---|
| **抖音** | 一律报 `Fresh cookies (not necessarily logged in) are needed` —— **即使不登录也强制要求带 Cookie**（坑 12） |
| **B 站** | 1080P+、番剧、会员内容需要登录态 |
| YouTube 部分内容 | 年龄限制视频同理 |

### 两种配法（二选一，也可以两个都填、文件优先）

在「**设置 → 登录态**」里：

1. **读取浏览器登录态** —— 最省事。选你平时登录那个站用的浏览器（Chrome / Edge / Firefox …）。
2. **用 cookies.txt 文件** —— 填一个自己导出的文件的绝对路径。

> **读浏览器登录态需要浏览器完全退出。** 浏览器开着时它的 cookie 数据库被锁住，
> 读不到。工具会把这种情况**明确翻译出来**，不会只把 yt-dlp 的原话甩给你：
>
> ```
> ⚠️ 浏览器正开着，Cookie 数据库被锁住了
>    把 Chrome 完全退出再试一次。如果不想关浏览器，改用导出的 cookies.txt……
> ```

### cookies.txt 必须是 Netscape 格式

浏览器插件默认导出的 **JSON 格式 yt-dlp 不认**。导出时请选
`Netscape` / `cookies.txt` / `Get cookies.txt` 这类选项。工具会检查格式并提前告诉你。

### 「测试登录态是否可用」按钮

设置页有一个测试按钮。它**真的会拿一个需要登录态的地址跑一次解析**，而不是只告诉你"已配置"。

为什么值得真跑一次：cookie 会**过期**、会被浏览器**锁住**、格式可能**不对** ——
这些都只有真跑一次才暴露。设置页写"已配置"毫无说服力，你要知道的是"现在能不能下"。

测试失败时给出的不是原始报错，而是**能照着做的下一步**：

| 引擎原话 | 工具给你的提示 |
|---|---|
| `Could not copy Chrome cookie database` | 浏览器正开着 → 完全退出再试，或改用 cookies.txt |
| `Fresh cookies … are needed` | 这个站要求带 Cookie → 去设置里配一个 |
| `failed to decrypt with DPAPI` | Chrome 新版加密解不开 → 更新 yt-dlp，或改用 cookies.txt |
| `Unsupported browser: xxx` | 浏览器名不认识 → 附上可用列表 |

### 隐私

- **默认不读任何 Cookie。** 必须由你在设置里显式开启 —— 工具不会"猜一个默认浏览器"然后偷偷读。
- Cookie 内容**不写日志、不入库、不回显**。诊断信息里只有"哪个来源、有没有读到"，没有内容本身。

### 已知摩擦

- Chrome 新版本的 cookie 加密方式偶尔会跑到 yt-dlp 前面。遇到 `failed to decrypt` 就
  **先更新 yt-dlp**（见第 11 节），不行再用 cookies.txt 绕开浏览器解密。
- 抖音即使配了 Cookie 也可能因为风控拒绝，那是站点侧的行为，不是工具问题。

## 9. 三期计划

> 状态：**已登记，按用户要求暂缓**。用户明确表示这个功能很实用，
> 但改动量大，先不做 —— 不是被否决，是排到后面。

### 列表页批量抓取（"把整个列表页扒下来"）

**现状**：粘 `https://www.xvideos.com/best/2026-08` 这类**列表页**会失败。
yt-dlp 不支持这种地址（试过把它当播放列表展开也不行），
现在只会给一句准确的说明 + 下一步建议（见坑 15）。

**目标**：粘一个列表页 → 自动列出页面上的所有视频 → 勾选/全选 → 批量入库排队。

**已有的基础**（三期不用从零开始）：

- `lib/urldiag.js` 的 `countVideoLinks()` 已经在解析页面里的视频链接了
  （实测 xvideos 列表页识别出 27 个、首页 48 个），三期只需把它从
  "返回数量"改成"返回链接列表"。
- `videos.url` 的唯一约束、批量入库、并发 2 + 限速的队列——
  这些批量下载需要的东西**一期就已经有了**。

**为什么改动量确实大**：

1. **提取方式需要两层兜底**
   - 第一层：直接读页面 HTML 里的 `<a href>`（上面说的 `countVideoLinks`）。
   - 第二层：有些站（B 站、部分 SPA）的列表是 **JS 动态渲染**的，
     HTML 里没有链接 —— 需要抓 JSON 接口或上无头浏览器。
     无头浏览器在当前沙箱里跑不起来（见坑 8），要么走 JSON 接口，要么另想办法。
2. **分页**：xvideos 这类页面通常只显示第一页，要跟 `?p=2` 这样的参数循环抓，
   必须设页数上限和限速，否则等于对站点做爬虫。
3. **先预览后下载**：不能粘一个链接就默默下 500 个文件。
   需要"解析出候选列表 → 展示（标题/时长/缩略图）→ 用户勾选 → 才入库排队"。
   这要新增一个预览界面（现在只有"提交后报告"，没有"提交前预览"）。
4. **逐条探测会很慢**：候选列表要显示标题就得对每个链接跑一次元数据解析，
   几十条会拖很久。需要并发探测 + 进度反馈 + 失败跳过，不能串行硬等。
5. **去重**：列表页每次抓到的可能是同一批视频，要复用现有的 URL 去重
   （`videos.url` 唯一约束已经在了），并明确告诉用户"新增 N 条 / 已有 M 条跳过"。

**必须守住的边界**（这条不能为了"实用"而让步）：

- 只抓**用户明确给出的那一个页面**（及其明确的分页），**不做全站爬取、不做站点镜像**。
- 页面级限速 + 页数上限，请求节奏要能被人看出来是"正常浏览"。
- 尊重各站 `robots.txt` 与服务条款；工具定位始终是**个人存档**，
  不提供任何批量传播能力。

**实现顺序建议**：先做"单页 HTML 提取 + 预览勾选"跑通闭环，
动态渲染的站（B 站等）放后面单独处理。

## 10. 命令行工具（给爱折腾的你）

```powershell
cd D:\AI\works\20260920_视频下载工具\app

node server.js        # 启动服务
node selftest.js      # 完整自检（111 项，含真实下载）

- 分析日志里有没有进度倒退、峰值速度多少
- 加 `--no-rate` 参数可以临时关掉限速做速度对比
